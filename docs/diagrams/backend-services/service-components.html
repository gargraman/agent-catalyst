Backend Services · 00 §3 · Major components per service

Five units, one shared library at the centre

The thin HTTP layer, the eval engine, ingestion, and the sandbox all import one pure runtime/ — no FastAPI, no HTTP types — which is exactly what lets them run identical code.

THE LOAD-BEARING RULE

runtime has no HTTP import

It takes a RunContext, yields StreamEvents. Three thin callers wrap it; none of its code knows whether it's serving a user, an eval, or a channel.

WHERE THE CARE GOES

Gateway + eval are ~10%

Cost is computed from our own capability profiles, never trusted from LiteLLM. The other ~90% (CRUD, versioning, token mint, export) is deliberately boring software with no model in it.

NOT PICTURED

web + worker

web is the Next.js console (a deployable unit, no backend modules of its own). worker is the arq/RQ process that runs evals & ingestion — it's the host, not a separate codebase.
