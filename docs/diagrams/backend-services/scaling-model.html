Backend Services · 11 · Scaling model

Scale the stateless tier out, the stateful core up

No app process holds tenant state in memory, so every unit scales horizontally on its own signal — concurrency or queue depth. The data core scales vertically, with HA where loss is unrecoverable.

WHY TWO WORKER POOLS

Don't let eval starve ingest

Eval + ingestion are bursty and token-heavy. A single pool lets a 120-case run starve a user's upload. Separate queues keep interactive jobs responsive while batch autoscales by depth.

COST vs LATENCY

Two different bounds

MAX_TOOL_CALLS bounds cost; the per-run deadline_s bounds latency. p99 ≤ 30s holds by construction, not by hope — and scale-out keeps first-token p95 < 2s under load.

THE STATEFUL CATCH

PgBouncer must be txn-mode

RLS pins the tenant with SET LOCAL app.workspace_id — this needs a transaction-scoped checkout. session pooling would leak the GUC across tenants. A correctness constraint, not a tuning knob.
